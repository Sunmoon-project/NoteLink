# 스터디룸 채팅과 자료 공유

작성일: 2026-11-11

이 문서는 대화에서 정리한 구현 방향이다. 아래 내용이 모두 구현·검증되었다는 뜻은 아니다.

## 기술 구성

- **모바일 앱:** 스터디룸 채팅 화면과 공유 자료 목록을 표시한다.
- **NestJS + Socket.IO:** 채팅 메시지와 자료 공유 이벤트를 방에 연결된 참여자에게 실시간으로 전달한다. 연결 인증과 이벤트별 방 참여 권한 검사는 서버가 담당한다.
- **MongoDB:** 채팅방, 메시지, 스터디룸 참여 상태와 자료 공유 관계를 저장한다. 실시간 연결이 끊긴 동안의 메시지는 저장된 기록에서 다시 조회한다.
- **Azure Blob Storage:** 공유 대상의 사진·파일 등 실제 파일을 저장한다. 파일 권한 확인과 접근 경로 발급은 기존 서버 정책을 따른다.
- **LiveKit Cloud:** 스터디룸의 캠·음성을 처리한다. 텍스트 채팅의 저장소는 아니다.

Firestore를 자료 공유에 반드시 추가하지 않고, 현재 NestJS·MongoDB·Blob 구조를 기준으로 진행한다. Socket.IO는 메시지를 영구 저장하는 DB가 아니므로 서버 저장과 재연결 시 누락 기록 조회가 필요하다.

## 채팅방과 메시지

- `chat_rooms`는 채팅방을 나타낸다. 스터디룸 채팅은 `studyRoomId`로 스터디룸과 연결한다. 일반 1:1 채팅도 별도의 채팅방으로 구분할 수 있다.
- `messages`는 각 메시지의 채팅방 ID, 발신자 ID, 종류, 내용, 생성 시각 및 필요 시 공유 항목 ID를 가진다.
- `text`는 일반 텍스트, `shared_item`은 퀴즈·플래시카드 등 공유 자료를 나타낸다.
- 메시지 수정·삭제 여부는 `editedAt`, `deletedAt` 같은 시각 필드로 표현하는 방안을 사용한다. 수정·삭제 권한과 화면 표시 정책은 별도로 확정해야 한다.
- 재전송 시 클라이언트가 생성한 `clientId`를 사용해 같은 메시지의 중복 저장을 방지한다.
- 서버 저장에 성공한 메시지를 같은 채팅방의 권한 있는 참여자에게 전달한다. 오프라인 사용자에게는 재접속 후 기록을 조회하도록 한다.

## 메시지 전송과 복구 규칙

- 보낸 사람의 화면에는 메시지를 즉시 `전송 중`으로 보여줄 수 있지만, 서버는 MongoDB 저장에 성공한 뒤에만 전송 성공을 알리고 참여자에게 전달한다.
- 서버 또는 DB가 저장 전에 중단되면 성공으로 표시하지 않는다. 앱은 실패·대기를 표시하고 복구 후 같은 `clientId`로 재시도한다.
- DB에 저장된 뒤 전달이나 응답이 끊겼더라도, 같은 방·발신자·`clientId`의 재시도는 기존 메시지를 반환해 중복 저장을 막는다. 다른 내용으로 동일한 ID를 재사용하면 거부한다.
- 재접속 시 서버 권한을 다시 확인하고 실시간 구독을 한 뒤, 최신 기록부터 이전 기록까지 50개씩 전체 조회해 중복을 제거한다. 연결이 중간에 끊어지면 부분 결과를 완료로 확정하지 않고 다시 동기화한다. 저장된 커서 이후만 조회하는 최적화는 아직 적용하지 않았다. `읽음 위치`는 별도로 관리해야 한다.
- 오래된 메시지의 수정·삭제를 지원할 때는 신규 메시지 커서만으로 복구가 불가능하다. 변경 이력 또는 별도의 동기화 전략을 먼저 마련한다.
- 전송 전에 계정·스터디룸별 기기 대기열에 메시지와 `clientId`를 기록한다. 방에 다시 접속하면 같은 ID로 재전송하며 서버의 성공 확인 이후 대기열에서 제거한다. 저장에 실패하면 입력을 지우거나 전송하지 않는다.

현재 구현 범위: 스터디룸 메시지 저장 후 Socket.IO 전달, `clientId` 중복 방지, 계정·방별 기기 전송 대기열, 50개씩 페이지를 읽는 전체 기록 재동기화. **메시지 수정·삭제 동기화는 아직 구현되지 않았다.** 일반 1:1 채팅도 별도 구현이 필요하다. 대기열 복원은 자동화 테스트에서 확인했으며 실제 기기 앱 종료·재실행 검증은 필요하다.

## 전체 기록 재동기화와 전송 대기열 구현

### 채팅 기록 복구

1. 앱이 스터디룸 채팅에 연결하면 서버가 방 참여 권한을 확인하고 Socket.IO 구독을 연결한다.
2. 구독이 완료되면 앱이 `GET /api/v1/chat-rooms/:id/messages`로 최신 메시지를 최대 50개 조회한다.
3. 받은 페이지의 가장 오래된 메시지 ID를 `before`에 넣어 이전 페이지를 반복 조회한다. 마지막 페이지까지 모두 읽으므로 누락이 50개를 넘어도 복구할 수 있다.
4. 페이지를 오래된 순서로 합치고 메시지 ID로 중복을 제거한다. 조회 중 들어온 실시간 메시지 및 전송 대기 메시지도 화면에 합친다.
5. 여러 페이지를 읽는 도중 연결이 끊어지면 조회를 완료한 것으로 처리하지 않는다. 재연결 후 방 구독부터 다시 진행한다.

이 방식은 저장된 마지막 동기화 위치 이후만 가져오는 방식이 아니라 **재연결할 때마다 전체 기록을 다시 조회**한다. 기록이 많아질수록 요청 횟수와 데이터 사용량이 늘어나므로, 이후 필요하면 읽은 위치와 변경 이력을 고려한 증분 동기화를 별도 설계한다. 메시지 수정·삭제는 아직 구현되지 않았다.

### 앱의 전송 대기열

1. 사용자가 메시지를 보내면 앱이 `clientId`, 채팅방 ID, 내용과 생성 시각을 계정·스터디룸별 기기 저장소에 먼저 기록한다.
2. 저장에 성공한 메시지는 화면에 대기 상태로 표시하고, 채팅방이 연결되어 있으면 Socket.IO로 전송한다. 기기 저장에 실패하면 입력 내용을 유지하고 전송하지 않는다.
3. 서버는 MongoDB에 저장한 뒤 성공 응답과 실시간 이벤트를 보낸다. 앱은 서버의 확인 또는 기록 조회에서 해당 메시지의 저장을 확인하면 기기 대기열에서 제거한다.
4. 앱을 종료했거나 연결이 끊긴 동안 남은 메시지는 같은 계정으로 해당 방에 다시 접속할 때 복원해 같은 `clientId`로 재전송한다. 서버가 이미 저장한 메시지는 중복 저장하지 않는다.

대기 메시지 내용은 기기 저장소에 보관되며, 실제 기기에서 앱을 완전히 종료한 뒤 다시 실행하는 시나리오는 아직 수동 검증이 필요하다.

### 확인한 테스트와 남은 검증

- 모바일 관련 테스트 16개 통과: 여러 페이지의 기록 조회, 중복 페이지와 중단 처리, 계정·방별 대기열, 화면 복원과 재연결 전송 등을 확인했다.
- 실제 MongoDB를 이용한 서버 채팅 테스트 13개 통과: 50개를 초과하는 기록의 페이지 조회와 메시지 중복 방지 등을 확인했다. API 빌드도 통과했다.
- 스터디룸 전체 모바일 테스트 실행 중 타이머 관련 테스트 하나가 실패했으나, 해당 테스트 묶음을 따로 재실행했을 때는 통과했다. 간헐적인 실패 원인은 추가 확인이 필요하다.
- 모바일 전체 타입 검사는 현재 설치되지 않은 `three`, `expo-gl` 관련 의존성 때문에 완료하지 못했다.
- 실제 iPhone에서 앱 종료·재실행, 네트워크 단절 및 DB 장애 복구를 종단 간으로 확인해야 한다.

## 참여와 보안 제약

- Socket.IO 연결 시 로그인 토큰을 확인한다. 방 입장, 메시지 전송, 기록 조회 및 자료 조회 때도 현재 권한을 검사한다.
- 스터디룸 채팅과 공유 자료는 **현재 해당 스터디룸에 참여 중인 사용자**만 접근한다. 방 ID나 초대 코드를 알고 있다는 사실만으로 채팅 또는 자료 접근을 허용하지 않는다.
- 자진 퇴장·강퇴 등으로 참여 권한이 없어지면 해당 방의 채팅·자료에 더 이상 접근할 수 없도록 한다. 이미 연결된 소켓의 수신도 중단해야 한다.
- 메시지 발신자와 공유자는 요청에 들어온 사용자 ID를 그대로 신뢰하지 않고 서버가 인증된 사용자로 결정한다.
- 메시지 길이·전송 횟수 등을 제한하고, 퀴즈를 공유할 때 공유자가 해당 원본에 접근하고 공유할 권한이 있는지 검사한다.

## 퀴즈·플래시카드 공유

- 공유할 때 원본을 복사하지 않고 **원본 ID를 참조**한다. 방 참여자는 공유 경로를 통해 읽기 전용으로 볼 수 있다.
- 참여자는 원본을 수정하거나 삭제할 수 없고, 내 보관함에 저장하는 기능은 제공하지 않는다. 퀴즈를 풀 때의 사용자별 풀이 결과는 원본과 별도의 기록이다.
- 원본이 수정되면 공유 화면에도 수정된 내용이 반영된다. 풀이 중 문제 변경을 어떻게 처리할지는 별도 결정이 필요하다.
- 기존 `room_shared_items` 스키마는 `roomId`, `sharedBy`, `quizSetId`, `flashcardIds` 등으로 방·공유자·원본 관계를 기록할 수 있다. 메시지는 공유 항목 ID로 이 기록을 참조한다.
- 자료를 열 때마다 서버는 현재 방 참여 여부, 공유 기록의 유효성, 원본의 존재·삭제 상태를 확인한다. 기존 소유자 전용 조회를 무조건 열지 않고 공유 전용 읽기 경로에서 권한을 확인한다.

## 공유 자료가 더 이상 유효하지 않을 때

- **원본 삭제:** 공유 자료를 열 수 없게 하고 채팅 및 자료 목록에 `삭제된 자료입니다`라고 표시한다. 기존 채팅 메시지는 대화 흐름을 위해 남긴다.
- **원본 소유자가 방에서 자진 퇴장하거나 강퇴됨:** 그 소유자의 공유 원본은 해당 방에서 더 이상 열 수 없게 한다. 채팅 및 자료 목록에는 실제 삭제와 구별해 `공유자가 방을 나가 볼 수 없는 자료입니다`라고 표시한다. 퀴즈 원본 자체를 삭제하지는 않는다.
- **공유자가 원본 소유자와 다른 경우:** 원본 소유자의 참여 상태와 공유자의 참여 상태를 구분해 확인한다. 공유자까지 방을 떠나면 공유를 유지할지는 팀에서 별도 결정한다.
- **조회자가 퇴장·강퇴됨:** 해당 방의 자료 조회를 거부한다. 채팅 메시지에 과거 자료 ID가 남아 있어도 이를 근거로 원본 접근 권한을 주지 않는다.
- 위 조건은 서버가 조회 때마다 확인한다. 별도 정리 작업이나 이벤트 반영이 늦어져도 원본을 그대로 노출하지 않는다.
- 소유자가 방에 다시 참여했을 때 기존 공유가 자동 복구되는지, 다시 공유해야 하는지는 아직 결정하지 않았다.

## 공유 자료 목록 UI

나중에 스터디룸 안에 **공유된 자료** 목록을 만들어 채팅이 오래 쌓여도 공유된 퀴즈와 플래시카드를 찾을 수 있도록 한다. 목록에는 자료 종류·제목·공유자·공유 시각을 표시하고, 유효하지 않은 자료에는 위 상태를 안내한다. 목록 조회에도 동일한 방 참여·원본 권한 검증이 적용된다.

## 남은 확인 사항

- 메시지 수정·삭제 허용 범위와 채팅 기록 보관 기간
- 공유자가 소유자와 다를 때의 퇴장 정책 및 소유자 재입장 시 공유 복구 정책
- 원본 수정 중인 퀴즈의 풀이 일관성과 사용자별 풀이 기록 저장 방식
- 강퇴·재접속 시 소켓 구독 해제, 누락 메시지 복구 및 중복 전송 테스트
- 일반 1:1 채팅의 친구 삭제·차단 이후 접근 정책
