# 약관 동의와 사용자 프로필 작업 정리

작성 기준: 2026-11-10, `feature/FR-01-user-profile` 작업 상태

요구 사항 번호
1. 약관 동의: 필수·선택 동의 여부를 서버에 저장
   - 요구사항 ID: FR-01 (회원가입 / 이용약관 동의)

2. 초기 프로필 설정: 닉네임, 학습자 유형, 관심 분야 저장 요청
   - 요구사항 ID: FR-03 (초기 프로필 설정)

3. 내 프로필 조회: 로그인한 사용자의 정보 조회
   - 요구사항 ID: FR-04 (내 프로필 조회)

4. 닉네임 중복 처리: 저장 시 중복 닉네임 차단
   - 요구사항 ID: FR-05 (닉네임 중복 검사 및 예외 처리)

## 구현 상태

### 약관 동의

- 기존 `POST /api/v1/auth/terms`가 로그인한 사용자의 동의를 저장한다.
- `service`와 `privacy`는 필수이며 `marketing`은 선택이다. 서버는 `users.termAgreements`에 약관 코드, 버전, 동의 여부, 시각을 기록한다.
- 프론트는 저장에 성공하면 프로필 설정 화면으로 이동한다.
- 이 기능은 이번 프로필 작업 전에 이미 구현되어 있었다.

### 내 프로필 조회와 저장

- `UsersModule`을 `AppModule`에 등록하고, JWT 인증이 필요한 `GET /api/v1/users/me`와 `PATCH /api/v1/users/me`를 작성했다.
- 조회는 토큰의 사용자 ID로 삭제되지 않은 사용자를 찾고 `toAppUser()`를 통해 앱에 필요한 정보만 `{ data }`로 반환한다.
- 초기 프로필 저장은 닉네임, 학습자 유형, 관심 분야 ID를 검증하고 사용자 문서에 반영한다. 닉네임 중복 키 오류는 `409 NICKNAME_TAKEN`으로 반환한다.
- 별도의 닉네임 중복 확인 API는 없다. 중복은 저장 요청 시 확인한다.

관련 코드: `apps/api/src/modules/users/`, `apps/api/src/modules/auth/terms/`, `apps/mobile/src/features/auth/auth.tsx`, `apps/mobile/src/features/profile/settings.tsx`.

## 확인한 테스트

| 항목 | 결과 | 범위 |
| --- | --- | --- |
| 약관 동의 테스트 | 11개 통과 | 서버 테스트; 실제 앱과 DB를 이용한 전체 흐름은 아님 |
| API 타입 검사와 빌드 | 통과 | 검사 당시 작업 코드 기준 |
| 내 프로필 인증 조회 | HTTP 200, 응답 사용자 ID 일치, 비밀번호 해시 등 민감 필드 제외 | 기존 사용자와 짧은 테스트 토큰 사용; 실제 앱 로그인 흐름은 미검증 |
| 닉네임 인덱스 | 실제 DB에 `nickname_1` 유일 인덱스 존재, 조회에서 인덱스 사용 | 로컬 MongoDB 읽기 전용 확인 |
| 닉네임 API 응답 시간 | 20회 성공, 전체 요청 4.28~48.45ms | 로컬 환경의 프로필 저장 요청; 운영 환경의 100ms 이내를 보장하지 않음 |
| 기존 닉네임 중복 | HTTP 409, `NICKNAME_TAKEN` | 임시 사용자로 실제 API 호출 |
| 동일 닉네임 동시 저장 | 요청 하나는 200, 다른 하나는 409; 같은 닉네임 저장 계정 1개 | 임시 사용자 2명으로 한 차례 동시 요청; 테스트 계정은 모두 삭제 |

프로필 저장 DTO 검증에서는 관심 분야를 선택하지 않은 빈 배열과 ObjectId 형식이 통과했고, 프론트가 현재 보내는 `수능` 같은 이름은 실패했다.

## 남은 작업

- 프론트는 관심 분야 이름을 보내지만 서버는 `categories`의 ObjectId를 요구한다. 카테고리 데이터를 준비하고 목록 API와 프론트 선택값을 ID로 연결해야 한다. 이름을 선택한 상태에서는 현재 저장이 실패한다.
- 현재 `PATCH /users/me` DTO는 닉네임, 학습자 유형, 관심 분야를 모두 요구한다. 설정 화면의 닉네임만 변경 또는 설정만 변경 요청도 같은 API를 사용하므로, 부분 수정 계약을 정하고 서버를 맞춰야 한다.
- MongoDB의 모든 `11000` 오류를 닉네임 중복으로 해석하지 않도록 실제 충돌 인덱스를 확인하는 처리가 필요하다.
- 프로필 조회·저장, 중복 처리와 동시성의 자동화 테스트를 추가하고, 실제 앱에서 로그인 → 약관 동의 → 프로필 저장 → 프로필 조회 흐름을 확인해야 한다.
- 온보딩 완료 여부는 현재 기기의 SecureStore에 저장된다. 다른 기기에서도 완료 상태를 유지하려면 서버에 완료 여부를 저장하고 로그인 흐름에 반영해야 한다.
- DTO 파일명 `update-profiile.dto.ts`의 오타를 수정할 때는 해당 import도 함께 바꾼다.

## 운영 및 개발 환경 참고

- 백엔드는 `npm run dev:api`로 실행하며 MongoDB는 별도로 실행한다. MongoDB 연결 정보는 `apps/api/.env`에 둔다.
- `MONGODB_URI`의 사용자·비밀번호, 인증 DB(`authSource`), URI 특수문자 인코딩을 확인한다. 접속 정보와 비밀번호는 문서나 커밋에 넣지 않는다.
- 프로필 탭은 `GET /users/me`를 사용하며 React Query 캐시의 기본 유효 시간은 30초다. 탭 재터치나 당겨서 새로고침 동작은 별도 구현 여부를 확인해야 한다.
